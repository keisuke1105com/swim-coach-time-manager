# 週次ランキング自動更新

## 動作

- GitHub Actionsが木曜21:17 JSTに開始（UTC木曜12:17）。公式サイトの更新曜日を保証するものではない。開始時刻はGitHub側の混雑で遅れる場合がある。
- 金曜06:17 JSTは未確認・未処理の種目だけ再試行する。手動実行も可能。
- アプリを開かなくても実行。activeで競技者IDがある選手の登録記録を種目・水路単位で重複排除する。調査時点で45名全員が対象。
- 既存の画面側と同じ本人照合・学年・種目・水路・2026年度処理を再利用し、登録済み複数IDの対応も維持する。JO・県強化突破率ランキングではなく、JASF同学年全国/県内順位の更新。
- 最短1.5秒間隔、逐次取得。1回2500リクエストまたは150分で打ち切り、未処理を保存。週次の実行が重複しないようconcurrencyを固定。API401/403/429はその回を停止し、アクセス制限を回避しない。
- 種目ごとに共有キャッシュへ保存。全国/県の一方しか取得できない場合は未確認扱い。以前の成功結果は残す。既存の最大40ページの県順位走査上限は維持するため、下位順位や学年不明・同姓同名等は未確認となる場合がある。
- 管理者の分析画面に最終確認日時、確認済み種目数、確認できた種目がある人数、未確認/未処理数を表示。4時間以上更新中のままなら中断の可能性を表示する。画面の再読み込み時に共有データを取得する。
- QR側は既存の公開同意・トークン確認を通じて同じ共有キャッシュから本人の順位を読む。データ公開範囲を変更しない。

## 公開時の設定（PR作成時点では未実施）

1. 最新の既存 `merge_swimmer_ranking_cache` 定義を再確認してバックアップする。
2. `supabase/setup/weekly-ranking-cache.sql` を適用。既存のSECURITY INVOKER/RLSを維持し、service_roleによる実行を追加する。更新日時を比較して古い端末からの逆戻りを防ぎ、成功結果を未確認で上書きしない。週次状況はservice_roleだけが更新できる。既存の記録テーブル・認証・QRのポリシーは変更しない。
3. GitHubリポジトリのActions secretsに `SWIM_SUPABASE_URL` と `SWIM_SUPABASE_SERVICE_ROLE_KEY` を登録。値はチャットやリポジトリのファイルに貼らない。service_roleはクライアントには渡さない。Actionsは公開レポートに氏名・競技者コード・生年月日・取得URLを出力しない。
4. mainへマージ後、workflow_dispatchで初回実行し、公式APIが実行環境から応答するか確認する。失敗時は既存順位が保持されること、分析画面に状態が表示されることを確認する。手動更新との競合で新しいキャッシュが古いキャッシュに戻らないことも確認する。
5. 木曜と金曜のスケジュールを確認する。停止はGitHubで当該workflowを無効化する。GitHubによるスケジュール無効化や失敗はActions画面でも確認する。

## 検証範囲と制約

`node tests/weekly-rankings.cjs`：画面と共通のID照合、種目/水路重複除外、対象外選手の除外、未確認結果による削除防止、更新状況の表示、全インライン構文を検証。既存の分析ランキングテストも実施。

PR作成時点では本番RPC置換、秘密情報登録、スケジュールの稼働確認、45名分の実取得を実施していない。SQLの実DB検証も公開前に必要。初回運用で所要時間と上限内での完了数を確認する。公式サイトの明示的な自動取得条件・更新曜日は確認できていないため、利用条件が示された場合は従う。

年度は既存アプリに合わせ2026を維持。2027年4月以降は誤った学年/年度で更新しないようランナーを停止する。次年度切替時にアプリと合わせて見直す。

## 初回実行での補正（2026-10-22）

GitHub上の初回実行ではDB接続・保存は成功したが、公式APIへの直接リクエストでアクセス制限応答となり、0/455種目で停止した。既存の順位は保持されている。GitHubの実行地域は既存の手動更新サーバーとは異なる。

今後は手動更新と同じ `jasf-ranking` サーバー経由で問い合わせる。サーバーは既存のコーチセッション認証を維持し、追加で環境変数のservice_roleキーと完全一致したサーバーワーカーだけを許可する。JWTのrole文字列だけでは許可しない。固定の公式ホストと検索パラメータ制限は維持し、サーバー経由でも401/403/429になれば停止する。この変更は関数の個別配備と再試行確認が必要。

初回の実DB検証でservice_roleのテーブル権限が不足していたため、ランキング共有キャッシュのSELECT/INSERT/UPDATEのみ付与した（適用済み）。SET ROLE service_roleによるトランザクションテストで、古い順位・未確認結果からの上書き防止を検証し、ROLLBACKでテストデータを残していない。RLSは有効、anonからのRPC実行は不可。

## 認証互換性修正（2026-10-30）

GitHubの登録済みキーはData APIの読み取り・進捗保存には成功するが、Edge Function内の環境変数キーとの完全一致判定を通らず、getUserで403、関数で401となっていた。APIキーはユーザーセッションではないため、getUserだけではワーカーの正当性を判定できない。

既存の完全一致とコーチのgetUser認証は維持し、不成立時に限り、受信した資格情報そのものをData APIへ渡して管理者限定の共有キャッシュ行をSELECTする。行が1件・既定job_key一致の場合だけ許可し、無効/anon/空行/別行は拒否する。検証通信障害時も許可しない。RLSと権限は変更しない。このテーブルを匿名公開してはならない。SDKは本番ログで使用されていた2.118.0へ固定。

テスト関数は実行後に常時410を返す実装へ置き換え済み。共有ランキング・選手・記録の書き込みは行っていない。
これは検索取得までの確認であり、全455種目の順位照合・保存・完走の検証ではない。
